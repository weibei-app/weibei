# 魏碑会话原生渲染统一计划

2026 年 9 月 5 日。用户已确认本计划并授权开工。开发基于最新主线 eb1fdb5e，在独立工作目录和同一个任务分支持续推进。此前的报告和各方原稿保留为论据，本文件统一后续工作的目标、范围、实现内容、协作分工和完成标准。

**方向：原生正文 + 成熟 Markdown 解析库 + 后台合并处理 + 界面按变化更新。完整计划确定后，作为一个任务连续开发，完成全部功能、接入、清理和验证，统一交付可体验的候选版。**

## 1. 最终要交付什么

| 用户行为 | 完成后的表现 |
|---|---|
| 看回答逐渐生成 | 内容持续出现；已显示内容不会因控件重建而清空、闪回或重播；持续输入时不会一直等待某份“最新结果”而停住显示 |
| 等待回答结束 | 最终内容完整；结束时沿用原来的显示，不因状态切换额外换版或跳位 |
| 阅读公式、代码、表格、图片 | 内容正确、清晰，保持现有阅读质量；需要的选择、复制和横向滚动可用 |
| 生成中向上翻、打开旧会话 | 阅读位置稳定，历史按需展开；新增内容不把正在翻阅历史的用户强拉回底部 |
| 调整窗口宽度 | 文字按新宽度正常换行，附件尺寸随内容正确更新，不靠冻结旧高度遮掩裁切或空白 |
| 打开资料、笔记或其他问答窗口 | 会话渲染不再重演旧候选版拖慢其他窗口的故障 |
| 打开历史记录，或在主聊天和浮动问答中阅读 | 已保存回答使用同一套原生正文；正文不再逐条等待网页编辑器启动，相关入口的富文本表现一致 |
| 读到正文中穿插的图示 | 图示保留在对应位置；生成结束时不会为了切换成图文混排而重新搭建整条回答 |

Markdown 语法闭合、图片到达和窗口变窄可以引起必要的重新排版。这里要求消除无故清空、重挂和阅读位置错乱，不承诺所有内容在任何时候都不移动。

最终拿到的是可实际使用的魏碑候选 App、完整接入的源码与评审材料，以及简短的体验和性能核对结果。原生化覆盖回答正文与常用富文本；专用图示和交互内容继续使用现有渲染能力。模型回答质量、网络出字速度不由本计划改变；内存和启动时间的改善幅度按实测报告，不提前承诺倍数。

## 2. 确定下来的技术方案

| 环节 | 执行决定 |
|---|---|
| 正文宿主 | 采用系统文字视图与第二代排版系统（NSTextView + TextKit 2）。每条回答的普通文字与段落在同一份文本中；生成和完成持续使用同一视图。公式、表格、代码、图片和专用内容按需要嵌入附件组件，维持同一正文结构 |
| 消息数据 | 继续使用现有消息模型、身份、保存方式和流式接收链路。原始消息保留完整内容，合并的只是显示工作 |
| 解析 | 使用 Swift Markdown 解析库；复用经过核对的公式整理等必要规则。后台解析当前回答，并计算内容、样式与附件的实际变化 |
| 调度 | 每条正在处理的回答只保留一个进行中的解析任务，期间收到的新内容合并为下一份。有效的新结果先显示，再处理下一份；避免输入不断到达时画面一直等待 |
| 变化应用 | 界面线程应用变化，复用未变化的文本及附件。比较尽量在后台对数据完成，不把全文逐属性比较、附件创建和多次全文替换堆到界面线程 |
| 结束、停止与切换 | 最终内容仍经同一条解析和显示路径应用；回答切换或源内容被改写时，旧任务不再影响新状态。保留现有停止和显示收尾语义 |
| 公式与其他富内容 | 原生公式使用 SwiftMath；审查复用既有代码高亮、表格、图片和复制等实现，重新接好承载、尺寸和交互。公式、代码、表格与来源链接随正文组件一并完成接入 |
| 排版和历史 | 先使用系统正常布局，沿用现有消息列表、历史按需展开和阅读位置逻辑。必要的尺寸缓存按内容、宽度、字号变化更新；不把旧缓存高度当成永久真值 |
| 相关入口 | 主聊天、浮动问答及其他现有会话正文入口复用同一正文组件；外层按钮、输入框、来源导航与业务行为沿用现有实现 |
| 专用内容 | 流程图（Mermaid）及交互内容继续使用现有专用渲染能力，接入新宿主；其中的网页组件不充当正文失败时的替代路径 |

后台解析可以重新处理整条当前回答，界面只应用实际差异；合法语法改变前文时，前文也要正确更新。这里不保证工作量永远只与尾部长度有关。

系统视图、显示中的附件和布局对象由界面线程管理；后台处理不随意访问它们。TextKit 2 是本计划选用的实现方案，其完整接入与实际性能须在开发中验证，不写成现成的性能成果。[苹果文字视图与附件说明](https://developer.apple.com/videos/play/wwdc2022/10090/)

### 2.1 输入、处理与显示的具体约定

| 位置 | 具体实现要求 |
|---|---|
| 现有消息接收 | 保留消息原文、消息身份、会话归属、来源和有序内容块。沿用现有流式显示泵的出字、停止和收尾语义，不增加另一套人为出字节奏 |
| 正文输入 | 宿主把消息身份、当前文本、有序内容块、生成状态、实际宽度、主题字号及链接操作传给正文组件。组件负责显示，不成为另一份会话数据或网络请求的管理者 |
| 来源与扩展整理 | 沿用已有来源引用、公式和魏碑扩展语法的语义规则；区分消息原文与用于显示的整理结果。解析库没有自动支持的扩展需要做必要适配，不能静默丢弃 |
| 后台解析 | 对当前回答的最新待处理快照解析；正在处理时只更新下一份待处理内容。已完成且仍有效的结果先应用，然后继续下一份；完成消息不订阅其他回答的逐字更新 |
| 差异更新 | 从文本、样式、附件类型及内容的实际差异确定修改范围。复用未变化的内容，批量应用相关修改；不会因每个新字重建全部附件，也不每次全篇清空再填入 |
| 选择与复制 | 更新不主动清空用户已有选区；变化影响选区时按对应文本位置调整。普通文字走系统选择，附件保留可读内容或对应源码的复制语义，整条回答复制沿用现有业务规则 |
| 完成与停止 | 正文包含最后一份有效内容后结束生成状态。停止、立即显示余文和切换会话继续遵守现有行为；上一条回答的后台结果不能应用到下一条回答 |
| 从历史重新打开 | 从现有已保存消息生成原生显示，不修改会话文件格式，不要求用户迁移历史内容 |

组件接线只提供本次需要的输入和回调。代码中的职责分开即可，不新建通用渲染插件体系、第二套状态管理框架或多引擎切换层。

### 2.2 正文与富内容的交付清单

| 内容 | 必须完成的显示与操作 |
|---|---|
| 中文、英文和基础样式 | 正文、标题、粗体、斜体、删除线、链接、分隔线、引用、嵌套列表和任务列表保留正确结构；中文阅读字体、行距、主题层级与魏碑现有风格一致 |
| 魏碑扩展 | 当前只读入口已启用的笔记链接、嵌入引用、行内脚注、提示块等迁移等效显示和已有交互；以实际只读入口为准，不把笔记编辑工具栏搬进聊天 |
| 行内及块级公式 | 接入 SwiftMath，处理数学字体、中文内容、行内基线、块级居中及宽公式的显示；从真实回答选取公式核对，复制保留有意义的公式内容，不变成空字符 |
| 代码 | 保留语言标记、原有高亮覆盖、缩进、空行和复制能力；较宽内容按现有产品行为换行或横向滚动，不能撑坏整个消息区。复用已有高亮资源或经过核对的归档实现 |
| 表格 | 正确处理表头、列对齐、行列增长、单元格文字与富内容、宽表横向滚动；选择和复制可用，不能把整张表变成不可交互的截图 |
| 图片 | 沿用当前资源定位和打开能力，保持比例；加载完成后的尺寸变更只更新受影响位置，替代文字和辅助功能内容保留 |
| 来源和动作 | 来源标签、材料定位、笔记链接、整条复制及现有摘录、替换、操作卡片等继续调用原业务入口；渲染改动不重写写笔记、确认动作等业务逻辑 |
| 图示和交互内容 | 复用现有图示与交互组件，保持在消息中的顺序、主题和已有操作；从生成到完成保留正文和附件身份，不把整条回答由一棵视图树切成另一棵 |
| 系统交互 | 基本文字选择、键盘复制、已有菜单、辅助功能标签与阅读顺序可用；保留减少动态效果设置，避免新动画反复改写文本样式 |

普通内容未写完时按当前已收到的内容合理呈现；完整语法到达后正确更新。不得把原先支持的内容长期显示成源码或纯文字，作为富文本接入完成的证明。

### 2.3 消息承载、滚动和尺寸

现有会话入口对带图示回答存在“生成时整篇正文、完成后按内容块重新搭建”的分支。新接入需要移除这次整体结构切换：文字和专用内容放在持续存在的正文结构内，图示就绪时只更新它自己的位置和尺寸。图示运行时继续复用，相关业务数据结构不重做。[现有会话内容入口](/Users/changfenhuang/projects/魏碑/Sources/WeiBei/Views/NotesAgentView.swift)

| 场景 | 处理方式 |
|---|---|
| 查看最新回答 | 沿用现有跟随最新内容的规则，不额外叠加由每次高度回报触发的强制滚动 |
| 向上阅读历史 | 保持当前阅读位置；新字、图片或附件尺寸变化不强拉到底部 |
| 展开更早消息 | 沿用历史展开策略和定位锚点，补入前文后仍能继续读原来的内容 |
| 拖动窗口、分栏和改变字号 | 使用实际宽度和样式更新必要布局；缓存只作可复用的结果或初始参考，不能把过期高度冻结成显示真值 |
| 未变化的已完成回答 | 不重复接收当前回答的流式发布；内容与显示对象保持稳定 |
| 远处内容 | 保留有实际用途的生命周期和尺寸管理，避免一边滚动一边反复创建销毁；不因原生化就取消按需历史或要求全部内容常驻 |

若采样仍指出列表反复测量，就修正对应的测量触发和行生命周期；这是完成原生会话的一部分，由主负责人处理，不重新立一个“先换列表”的项目。

## 3. 一个完整任务，连续开发并统一交付

开工后按第 2 节完整范围连续实现：原生正文与富内容、全部相关会话入口、历史和阅读位置、现有交互与辅助功能、旧路径清理、验证及候选包。组件实现、集成和调试的先后由开发者根据实际依赖自行安排，不设置独立原型阶段或阶段间审批。

开发中使用真实回答和长会话检查功能、定位并修复问题，持续完成计划内的剩余工作；不以单条回答能显示或局部组件可运行作为任务完成。最终统一交付完整候选版及检查、评审材料，用户集中体验最终结果。实现、本地检查、CI、合并和实际体验状态分别如实记录。

遇到实际卡顿，沿采样定位解析、附件、排版或列表中的具体重复工作并修复。只有证据表明现有做法不足时，才增加对应优化，不预先引入完整后台排版框架。

### 3.1 子智能体分工与强度

用户确认后，通常同时安排两名子智能体。主负责人先从最新主线核对调用关系、确定必要的数据接线和文件归属，再派发明确任务；以下分工是同一个开发任务的内部协作，不是交付阶段。

| 负责人 | 负责的具体工作 | 模型与强度 |
|---|---|---|
| 主负责人（本任务） | 统筹方案和接口；管理分支及合并请求；依赖接入、共享核心文件、聊天宿主与混合内容接入；整合、问题归因、审查、验证和最终交付 | 保持本任务，由主负责人统一作实现取舍 |
| 子智能体 A | 原生正文、Markdown 转换、流式解析合并与差异应用；维护其直接相关的小型回放检查 | 与主任务相同的模型，推理强度 `medium` |
| 子智能体 B | 公式、代码、表格和图片附件；复用原有能力，完成尺寸、复制、主题与必要交互 | 与主任务相同的模型，推理强度 `medium` |
| 有界的后续核对 | 由已完成任务的子智能体承担资料或调用核对；需要审查时交叉检查另一部分的实际代码 | 与主任务相同的模型，推理强度 `medium` |

按用户本轮指定，子智能体继承主任务的模型，推理强度统一设为 `medium`，替代此前的 `gpt-5.6-sol` 与 `high` 安排；主任务自身配置保持不变。不为每个小功能继续增加子智能体，也不让子智能体自行派生团队。启动时核对工具返回的实际模型和推理配置；能读取而与请求不符时先纠正，不继续盲目增加任务。

## 4. 范围与取舍

| 采用并完成 | 本次不纳入 |
|---|---|
| 原生正文及现有常用富文本能力，完整接入相关聊天入口 | 整场单页网页路线的并行实现 |
| 原生系统支持的附件承载、正确尺寸与现有交互 | 为后台并行测量预先建立“纯数据尺寸 + 前台叠加视图”的完整框架 |
| 成熟解析器、输入合并与实际差异应用 | 自研七类语法提交状态机 |
| 按需展开历史、必要的布局管理和真实热点优化 | 全历史常驻内存、先重写列表、以清空所有缓存为目标 |
| 同一正文组件持续显示至完成 | 生成结束时切换到另一套静态渲染器 |
| 保留既有内容能力与辅助功能，修好新承载中的接线 | 顺带重做笔记编辑器、资料阅读器或整个应用界面 |

系统文字控件提供选择、菜单和辅助功能的基础，但附件内容复制等仍需接好。跨消息连续选区、全会话新搜索等能力不作为原生化自动获得的成果，也不顺带扩成新功能项目。

清理以调用关系为准：只删除本次已替代且无其他用途的代码。其他阅读或编辑入口仍使用的网页能力，以及专用图示所需的承载，继续由其使用。

## 5. 验证保持精简，但要能证明结果

| 验证 | 做法 |
